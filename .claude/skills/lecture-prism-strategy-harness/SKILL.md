# lecture-prism Strategy Harness Lite

이 스킬은 `revfactory/harness`의 “도메인별 에이전트/스킬로 작업을 안전하게 구조화한다”는 아이디어를 lecture-prism 강의용으로 줄인 것이다.

목표는 수강생이 개떡같이 말해도 다음 흐름이 자동으로 일어나게 하는 것이다.

1. 말에서 전략 의도를 뽑는다.
2. Part 4 트랙 A/B/C/D 중 가장 안전한 1개를 고른다.
3. 최소 파일만 수정한다.
4. API 키 없이 데모 모드로 실행 검증한다.
5. 초보자에게 “무엇을 바꿨고 왜 결과가 달라졌는지” 설명한다.

사용자는 비전공자일 수 있다. 전문 용어보다 결과를 먼저 말하고, `adapter`는 `데이터 연결 부품`, `schema`는 `결과 모양`, `fallback`은 `안 되면 대신 쓰는 방법`처럼 쉬운 말로 풀어 쓴다.

## 언제 사용하나

다음 표현이 있으면 이 스킬을 사용한다.

- “내 전략 반영해줘”
- “MY_STRATEGY.md 읽고 바꿔줘”
- “하네스 써서 알아서 해줘”
- “과매도 반등 전략으로 바꿔줘”
- “손절을 좀 타이트하게”
- “현금 비중을 더 남기고 싶어”
- “수강생 실습 도와줘”
- “뭘 바꿔야 할지 모르겠는데 알아서 추천해줘”

## 기본 원칙

- 수강생에게 명령어를 치라고 하지 않는다. 필요한 실행은 에이전트가 한다.
- 질문은 최대 1개만 한다. 합리적 기본값으로 진행 가능하면 묻지 않는다.
- 한 번에 1개 트랙만 구현한다. 욕심내서 전부 바꾸지 않는다.
- 전략이 여러 트랙에 걸치거나 수강생이 “전부 반영해줘”라고 해도 한 번에 다 수정하지 않는다. 트랙 순서를 먼저 제안한 뒤, **[한 트랙 수정 → 데모 검증 → 전후 비교 보고] 사이클을 트랙별로 반복**한다. 한 사이클에 한 트랙.
- 실거래 금지. KIS 실제 주문, `--live`, 실제 인증 파일 수정 금지.
- API 키 없이 데모 모드에서 검증 가능해야 한다.
- 함수 시그니처를 유지한다.
- 새 의존성을 추가하지 않는다.
- 시크릿, token, `prism.db`는 커밋 대상으로 만들지 않는다.

## 수업 빠른 모드 (기본)

35분 수업에서는 수업 빠른 모드를 기본으로 사용한다.

1. `MY_STRATEGY.md`, 이 스킬의 트랙 지도, 선택한 트랙의 대상 파일 하나를 먼저 읽는다.
2. 질문은 최대 하나만 하고, 답이 없어도 안전한 가정으로 진행할 수 있으면 묻지 않는다.
3. 한 트랙만 수정하고 관련 데모와 전체 mock 파이프라인을 검증한다.
4. 외부 데이터 장기 조사, 여러 트랙 동시 수정, ETF·선물·코인 확장은 보고서의 “다음에 할 일”로 남긴다.
5. 사용자가 `심화 모드`라고 명시한 경우에만 다음 트랙이나 외부 연동으로 범위를 넓힌다.

목표 시간은 전략 작성 3~5분, 수정 10~15분, 검증 5~10분이다. 시간 안에 끝내기 어렵다면 검증을 줄이지 말고 수정 범위를 더 작게 잡는다.

## System Completion Lane

System Completion Lane은 다섯 번째 전략 트랙이 아니다. A/B/C/D 중 한 트랙을 **수정 → API 키 없는 데모 검증 → 전후 비교**까지 끝낸 뒤에만 진행한다. 전략을 더 고치는 단계가 아니라, 그 전략이 들어간 한 번의 실행을 끝까지 설명할 수 있는지 확인하는 단계다. 상세 체크리스트는 `references/system-completion.md`를 읽는다.

다음 증거는 모두 같은 `run_id`를 가리켜야 한다.

- `data_as_of`: 휴장일이면 오늘 날짜로 꾸미지 않고 실제 최근 영업일을 표시한다.
- `sequence`: 파이프라인 시작부터 완료 또는 실패까지 증가하는 순서를 확인한다.
- Discord: 3주차 필수 준비 채널이다. 전송 실패는 기록하되 파이프라인은 계속되는지 확인한다.
- Telegram: 선택 채널이다. 설정했다면 Discord와 같은 `run_id`·`sequence`를 받는지 확인하고, 없으면 “선택 채널 미설정”으로 남긴다.
- 주문: `accepted`, `partial_fill`, `filled`, `blocked`, `live_blocked`를 바꿔 말하지 않는다. `accepted`는 체결이 아니며, `partial_fill`을 포함한 실제 `filled_qty`만 포트폴리오에 반영한다.
- 대시보드: 이벤트·알림·주문·분석 6섹션·교훈이 선택한 실행 하나에서 왔는지 확인한다. 모르는 현금 잔고나 평가액을 만들어내지 않는다.

기본 mock/simulation 검증은 알림 또는 KIS 키가 없어도 완주해야 한다. 실제 Discord·Telegram 메시지는 로컬 `.env`에 해당 채널이 설정된 경우에만 보내고, KIS 모의투자 API 호출은 사용자가 안전 플래그를 명시적으로 허용한 경우에만 한다. 실전 주문은 항상 `live_blocked`여야 한다. 웹훅 URL, 봇 토큰, 계좌번호, `.env` 원문은 출력·제출·커밋하지 않는다.

## 트랙 선택 규칙

| 트랙 | 파일 | 선택 조건 | 난이도 |
|---|---|---|---|
| A | `screening.py` | RSI, 거래량, 시총, 이동평균, 신고가 등 정량 진입 조건 | 쉬움 |
| B | `analysis.py` | 피터 린치, 그레이엄, 오닐, 뉴스/재무/모멘텀 관점 등 분석 프롬프트 | 쉬움 |
| C | `trading.py` `_decide_exit` | 목표가, 손절, 트레일링 스탑, 절반 청산 등 청산 규칙 | 보통 |
| D | `trading.py` 상수 | 최대 종목 수, 현금 비중, 매수 점수, 손절폭 등 리스크 원칙 | 쉬움 |

판단이 애매하면 아래 우선순위를 따른다.

1. 숫자가 있는 진입 조건이면 A
2. 철학/관점/스타일이면 B
3. 언제 팔지 이야기하면 C
4. 얼마나 살지/현금/종목 수 이야기하면 D
5. 정말 불명확하면 B를 추천하되, 구현 전 수강생에게 “분석 관점부터 바꿔볼까요?”라고 1개 질문

## 작업 흐름

### 1. 전략 입력 수집

먼저 아래를 읽는다.

- 사용자 메시지
- `MY_STRATEGY.md`가 있으면 그 내용
- `README.md`의 하네스 안내
- `lecture/exercises/part4_실습가이드.md`의 트랙 설명

### 2. 전략 정리

내부적으로 다음 구조로 정리한다.

```text
목표:
진입:
분석 관점:
청산:
리스크:
시장 흐름:
필요한 자료:
직접 넣을 자료:
기억:
향후 확장:
서로 충돌하는 조건:
확실히 말한 것:
하네스가 우선 가정한 값:
이번 범위 밖:
추천 트랙:
```

모순이 있으면 실거래 안전과 손실 제한 → 사용자가 직접 말한 숫자 → 청산·위험 → 진입 → AI 판단 순서로 정리한다. AI 판단은 코드로 고정한 안전장치를 넘지 못한다. 모순이 남으면 질문 하나만 하거나 두 mock 시나리오를 비교한다.

### 2-A. 자료 준비 상태

필요한 자료마다 아래 다섯 상태 중 하나를 붙인다.

| 자료 준비 상태 | 뜻 | 하네스 행동 |
|---|---|---|
| 지금 사용 가능 | 프로젝트에 이미 있음 | 기존 값을 재사용 |
| 무료 연결 가능 | 결제·로그인 없이 연결 가능 | 공식 문서와 이용 조건 확인 후 데이터 연결 부품 제안 |
| 키 또는 계정 필요 | 발급이나 로그인이 한 번 필요 | 용도·공식 발급 위치·환경변수 이름·비용 가능성·mock 대안 안내 |
| 사람이 넣어야 함 | 자동 접근이 어렵거나 유료 자료 | UTF-8 텍스트나 Markdown 입력 형식과 로컬 저장 위치 안내 |
| 이번 범위 밖 | 상품 구조나 안전 조건이 크게 다름 | 선행 조건과 별도 확장 과제로 분리 |

키나 계정이 없어도 중단하지 않는다. mock 또는 사용자가 제공한 예시 자료로 먼저 검증한다. 키 값은 채팅에 붙이지 말고 `.env`에 넣도록 안내한다. 유료 자료 원문과 캡처는 `student_inputs/`에 두며 Git에 올리지 않는다.

### 3. 최소 수정

선택한 트랙에 해당하는 파일만 우선 수정한다.
여러 트랙이 필요한 전략이면 이번 사이클에서는 첫 트랙만 수정하고, 나머지 트랙은 보고의 “다음에 바꾸면 좋은 것”에 순서대로 남겨 다음 사이클에서 처리한다.

- A: `screening.py`
- B: `analysis.py`
- C: `trading.py`
- D: `trading.py`

수정 전후 비교를 위해 가능하면 변경 전 실행 결과를 먼저 확보한다.

### 4. 검증

트랙별 검증 기준:

- A: 스크리닝 단독 실행 + 전체 파이프라인 데모 실행
- B: 단일 종목 분석 실행 + 가능하면 전체 파이프라인 데모 실행
- C: 청산 데모 실행
- D: 시뮬레이션 매매 실행

공통 검증:

- 변경 파일 Python compile 통과
- macOS·Windows에서 쓸 수 있는 경로인지, Python 3.10 문법인지 확인
- 실거래 경로가 실행되지 않았는지 확인
- 시크릿, `student_inputs/`, 실제 계좌·대시보드 원본이 변경·스테이징되지 않았는지 확인
- 한 트랙 검증 뒤 System Completion Lane을 진행했다면 `run_id`, `data_as_of`, `sequence`, 알림 전달, 주문 상태, 대시보드가 서로 같은 실행인지 확인

### 5. 보고

수강생에게는 전문 용어보다 쉬운 말로 설명한다.

```markdown
## 이번에 반영한 전략
-

## 바꾼 파일
-

## 왜 이 트랙을 골랐나
-

## 검증 결과
-

## 다음에 바꾸면 좋은 것
-

## System Completion Lane
- 실행 진실:
- 알림 전달:
- 주문 진실:
- 대시보드 증거:
- 시크릿 점검:
```

## “개떡같은 말” 해석 예시

| 수강생 표현 | 해석 | 추천 트랙 |
|---|---|---|
| “너무 오른 건 말고 눌렸다가 튀는 애들” | 과매도/반등 진입 조건 | A 또는 B |
| “손절 좀 빨리” | 손절폭 축소 | C |
| “겁나게 몰빵하지 말고” | 종목 수/현금 비중/포지션 크기 제한 | D |
| “뉴스 좋은 애만” | 뉴스 분석 프롬프트 강화 | B |
| “거래량 터진 애” | 거래량 급등 조건 | A |
| “가치투자 느낌” | 분석 프롬프트를 가치/재무 관점으로 변경 | B |

## 에이전트 역할

이 하네스는 다음 로컬 에이전트 정의와 함께 쓰면 좋다.

- `lecture-strategy-interviewer`: 애매한 전략을 트랙 요구사항으로 정리
- `lecture-strategy-implementer`: 최소 파일 수정 및 데모 검증
- `lecture-strategy-verifier`: 의도 반영, 안전, 검증 결과 확인

Codex 환경에서는 필요할 때 이 역할 이름의 서브에이전트를 사용할 수 있다. Claude Code 환경에서는 같은 역할 설명을 프롬프트로 전달해도 된다.

## 금지

- 실거래 주문 실행
- 수강생에게 터미널 명령어를 직접 치라고 안내
- 한 번에 여러 트랙을 동시 수정 (여러 트랙 요청은 한 트랙씩 순차 사이클로)
- API 키 없이는 아무것도 못 한다고 중단
- 검증 없이 “완료”라고 말하기
- 비전공 사용자에게 전문 용어만 나열하기
- API 키나 유료 자료 원문을 채팅 또는 Git에 붙이게 하기
