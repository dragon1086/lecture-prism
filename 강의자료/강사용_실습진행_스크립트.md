# 강사용 실습 진행 스크립트

> 파트 3·4는 각각 120분입니다. **핵심 90분 + 질문·오류·개별 지원 30분**으로 운영합니다.
> 이 문서는 강사 전용 로컬 자료입니다. 수강생은 [파트 3 프롬프트](../lecture/exercises/수강생_붙여넣기_프롬프트_파트3.md), [파트 4 프롬프트](../lecture/exercises/수강생_붙여넣기_프롬프트_파트4.md)에서 강사가 부르는 번호 하나만 복사합니다.

## 이 강의의 한 문장

> 비전공자도 **내 투자 북극성을 한 문장으로 말하고, AI에게 한 파일의 한 규칙으로 구현하게 한 뒤, 바뀐 결과의 근거를 읽을 수 있다.**

이 수업은 수익률 경연이나 실계좌 연결 수업이 아니다. 사람은 전략과 책임을 정하고, 코딩 에이전트는 조사·수정·검증을 돕는다. 수강생은 명령어 암기 대신 아래의 학습 루프를 반복한다.

1. **질문한다.** “내 북극성에서 지금 무엇을 검증하려는가?”
2. **예측한다.** “이 프롬프트가 무엇을 바꾸고, 무엇은 건드리지 않을까?”
3. **작게 실행한다.** 한 번에 프롬프트 하나, 파일 하나, 규칙 하나만 다룬다.
4. **증거를 읽는다.** 로그·표·바뀐 코드 차이(diff)·테스트 중 하나를 찾는다.
5. **회고한다.** “내 전략 → 바꾼 파일 → 달라진 결과”를 한 문장으로 말한다.

이 다섯 단계를 매번 소리 내어 짧게 반복한다. “이해되셨죠?” 대신 “이걸 내 전략의 어디에 쓸 수 있을까요?”, “실행 전 무엇이 나올 것 같나요?”를 묻는다.

## 말부터 쉽게 맞추기

| 강의에서 먼저 쓰는 말 | 필요한 경우의 기술 용어 | 강사 설명 |
|---|---|---|
| 연습 데이터 | mock | 오늘 시장이 아니라, 같은 결과를 다시 확인하도록 준비한 고정 연습 재료 |
| 가상 체결 | simulation | 증권사에 주문을 보내지 않고 ‘이 조건이면 샀을 것’을 남기는 연습 |
| 작업 흐름 | pipeline | 후보 찾기 → 자료 읽기 → 가상 판단 → 기록 남기기의 순서 |
| AI 작업 도우미 | agent | 조사·코드 수정·검증을 역할별로 돕는 AI |
| 글과 자료를 읽는 AI | LLM | 뉴스·설명처럼 정답 하나가 없는 문맥을 요약하는 AI |
| 구독 계정 로그인 | OAuth | API 키 대신 공식 도구의 로그인 상태를 쓰는 선택 연결 방식 |
| 실데이터 | real_data | 실제 가격·거래량을 쓰되, 실패하면 연습 데이터로 돌아가는 선택 경로 |
| 판단 알림 | Discord | 계좌 정보 없이 이번 실행의 후보·분석·매매 판단을 보내는 선택 알림 |
| 기본 경로로 돌아감 | fallback | 선택 연결이 실패해도 연습 데이터 경로로 수업을 계속하는 설계 |
| 매수 보류 권한 | HOLD veto | LLM이 불확실하면 BUY를 HOLD로 낮출 수만 있는 안전 권한 |

## 강사가 계속 지킬 안전 문장

다음 세 문장을 파트마다 한 번씩 반복한다.

> 매수 에이전트의 BUY는 실제 주문이 아닙니다. 오늘 모든 매매는 가상 체결입니다.
>
> 점수·목표가·손절가는 코드 규칙이 정합니다. LLM은 설명을 보태고 불확실하면 HOLD를 제안할 수만 있습니다.
>
> 오류·실데이터 실패·로그인 실패는 감출 일이 아닙니다. 연습 데이터로 돌아가는 것도 설계가 제대로 작동한 증거입니다.

## 수업 전 공통 준비

### 수강생 사전 준비

수업 시작 10분 전에 [수업 시작 전 안내](수업_시작_전_안내.md)를 LMS와 강의 채팅에 배포한다. 수강생은 Codex 또는 Claude Code 중 하나를 고르고, 원하는 위치에 빈 폴더를 만든 뒤 그 폴더를 작업 공간·프로젝트 폴더로 선택한다. 이미 시작한 채팅창에 안내의 저장소 복제 프롬프트와 공통 환경 준비 프롬프트를 차례로 붙여넣으면 에이전트가 현재 작업 공간에 공개 `lecture-prism` 저장소와 프로젝트 전용 `.venv`를 만들고 `requirements.txt` 전체를 설치한다. GitHub 계정은 공개 저장소 복제에 필요하지 않으므로, 계정 생성·GitHub 로그인·터미널 사용을 수업 시작 조건으로 만들지 않는다.

수업이 시작되면 수강생의 Codex 또는 Claude Code 작업 공간에 `lecture-prism` 프로젝트 루트와 수강생 프롬프트 파일이 보이고, 프로젝트 루트의 `.venv`가 준비된 상태여야 한다. IntelliJ는 필요하지 않으며, Finder나 탐색기에서 폴더만 열어 둔 상태는 준비 완료로 보지 않는다. 복제나 환경 준비가 막힌 수강생은 오류 화면을 그대로 두고, 강사가 순회하며 사전 안내 프롬프트를 다시 쓰게 한다.

1. 강사용 시연 폴더는 수강생과 같은 깨끗한 복사본으로 준비하고, Python 3.10 이상으로 프로젝트 루트의 `.venv`를 만든다. 실데이터·Discord 시연이 실패해도 `.env` 없이 연습 데이터(mock)로 돌아갈 수 있어야 한다.
2. 강사용 `.venv`에는 수강생과 같은 방식으로 `requirements.txt` 전체를 설치한다. 외부 패키지 설치나 실데이터·Discord 실행에 네트워크 승인이 필요하면, Codex·Claude Code가 필요한 도메인에 대한 **범위 제한 네트워크 승인**을 요청하게 한다. 전역 샌드박스를 끄거나 권한을 통째로 우회하지 마. P3-01은 `005930 한 종목`의 `real_data + Discord + simulation` 전체 흐름으로 수업 전에 한 번 점검하고, 권한·DNS·Yahoo 429·Discord 중 하나가 막히면 mock 전체 실행으로 즉시 전환한다. 공식 Codex OAuth `research`는 P3-M2가 끝난 뒤 준비 상태별 A/B 분기로 진행하므로, 강사는 실제 LLM 성공 결과와 읽기 전용 증거를 모두 준비한다.
3. KIS 실제 키는 강의 화면 및 공유 자료와 분리한다. 강사는 `.env.example`을 복사한 로컬 `.env`를 운영체제의 기본 텍스트 편집기로 열어 App Key와 App Secret을 직접 입력한다. Part 4에서는 real 환경의 가격·일별 투자자 수급만 읽으므로 계좌번호·HTS ID·`trading/trading/config/kis_devlp.yaml`은 필요하지 않다. 이 YAML은 모의·실거래 브로커 심화에서만 다룬다. 주문·취소·정정·잔고·계좌 API는 호출하지 않고 매매는 simulation으로 유지한다.
4. 강사용 첫 화면에는 `실데이터(yfinance) + Discord` 성공 증거 또는 mock 증거 하나를 준비한다. 실제 Discord 증거에는 예정된 알림 순서가 아니라 실제 전송 성공 건수와 실패 원인을 남긴다. 수업 중에는 Python·가상환경·패키지·OAuth 설치를 기다리지 않는다.

### 리허설 프롬프트 1 · 강사와 수강생의 첫 전체 실행 경로 점검

```text
lecture-prism 강사용 시연 폴더에서 P3-01 첫 전체 실행을 수업처럼 한 번 점검해줘.

조건:
1. API 키·증권사 인증 파일·기존 계좌 설정은 읽거나 만들거나 바꾸지 마. `.env`가 있더라도 웹후크 주소는 화면이나 답변에 출력하지 마.
2. 패키지를 설치하거나 설정 파일을 바꾸지 말고, yfinance와 기존 Discord 설정이 모두 준비되어 있는지만 확인해줘.
3. 둘 다 준비되어 있으면 Yahoo Finance와 Discord에 필요한 범위 제한 네트워크 승인을 먼저 요청해줘. 전역 샌드박스를 끄거나 권한을 통째로 우회하지 마. 별도 DNS·HTTP 점검을 반복하지 말고, 승인된 뒤에만 `real_data` 프로필, `005930 한 종목`, `dry-run`으로 `main.py` 다섯 단계 전체 흐름을 한 번 실행해줘. 후보 확인 → 종목별 분석 → 매매 판단 → 판단 요약 → 피드백 저장 알림이 이어지는지 확인해줘.
4. 네트워크 권한 미승인·DNS 실패·Yahoo 429·Discord 실제 전송 실패가 나면 자동으로 다시 시도하지 마. 실패 원인을 하나로 구분한 뒤 `LECTURE_PROFILE=mock`, `LECTURE_NOTIFY_DISCORD=0`으로 외부 연결을 끈 mock + simulation 경로를 한 번 완주해줘.
5. 스크리닝 → 분석 → 매수 시나리오 → 시뮬레이션 매매 → 피드백·저장이 모두 끝나는지 확인해줘.
6. 데이터 원천이 `실데이터(yfinance)`인지 `mock`인지, Discord 실제 전송 성공 건수와 실패 원인, 실제 주문·브로커 API 호출이 0회임을 로그로 확인해줘. 예정된 알림 순서와 실제 도착을 같은 뜻으로 말하지 마.
7. 성공하면 선택한 경로, 후보 종목, 추천·점수, 시뮬레이션 체결 수, Discord 실제 전송 성공 건수만 짧게 정리해줘.
8. 실패하면 .env·시크릿·브로커를 건드리지 말고 mock으로 전환한 이유와 수업에서 읽을 증거만 알려줘.
```

### 리허설 프롬프트 2 · 강사 전용 선택 연구 확인과 첫 화면 증거 만들기

```text
lecture-prism 강사용 시연 폴더에서 실데이터와 공식 Codex OAuth 분석을 수업 전에 안전하게 점검해줘.

조건:
1. 실제 주문·브로커 API·KIS/키움/토스 설정은 절대 읽거나 호출하거나 바꾸지 마. 모든 매매는 simulation으로 유지해.
2. 먼저 Yahoo Finance 연결에 필요한 범위 제한 네트워크 승인을 요청해줘. 전역 샌드박스를 끄거나 권한을 통째로 우회하지 마. 승인이 끝난 뒤 삼성전자 005930 한 종목만 real_data로 한 번 분석해줘. yfinance 실제 데이터 성공인지 mock 폴백인지 source와 기준일·현재가를 구분해 알려줘.
3. 그 다음 공식 Codex CLI의 로그인 상태만 사용해 research + oauth로 같은 종목을 한 번 분석해줘. 이 단계는 `codex exec`가 기존 로그인 상태를 읽을 수 있도록, 코딩 에이전트가 이번 research + oauth 실행에만 쓰는 **승인된 외부 실행**을 한 번 요청한 뒤에 진행해. 전역 샌드박스를 끄거나 권한을 통째로 우회하지 마. `codex exec`를 따로 점검하거나 여러 번 실행하지 말고, main.py의 단일 종목 흐름 안에서만 쓰게 해. 토큰·인증 파일은 읽거나 출력하거나 복사하지 마. Perplexity와 Firecrawl은 사용하지 마.
4. Yahoo 429·네트워크 권한 미승인·DNS·Codex CLI 호출 오류가 나면 자동으로 다시 시도하지 말고, 실제 LLM 호출 성공인지 규칙 폴백인지 로그로 구분해 데이터 원천·추천·매수점수·목표가·체결 수를 정리해줘. 응답 형식 불일치나 섹션별 규칙 폴백은 호출 실패가 아니므로, 그 사실만 기록하고 실행을 다시 시작하지 마.
5. 실제 LLM이 정량 점수·목표가·손절가를 올릴 수 없고 HOLD veto만 할 수 있는지 결과와 코드 경계를 함께 확인해줘.
6. yfinance 데이터 조회 또는 Codex CLI 호출 자체가 실패했을 때만 원인을 짧게 기록한 뒤 .env를 남기지 않는 mock 시뮬레이션으로 즉시 한 번 완주해줘. 응답 형식 불일치나 규칙 폴백만으로는 mock을 추가 실행하지 마. 이 경우 실데이터 research 결과를 그대로 기록하고, 강사용_첫화면_연구증거.txt에 실제 LLM 호출 성공과 섹션별 규칙 폴백을 나눠 적어줘. mock을 실행했을 때만 생성된 mock 보고서 옆에 강사용_첫화면_mock증거.txt를 만들어, mock 데이터·규칙 폴백·추천·매수점수·목표가·체결 수만 8줄 이내로 적어줘.
7. 성공한 research 보고서는 강사용 로컬 reports/에만 남기고 Git에 추가하지 마. 같은 폴더에 강사용_첫화면_연구증거.txt도 만들어, 데이터 원천·실제 LLM 성공 또는 규칙 폴백·추천·매수점수·목표가·체결 수만 8줄 이내로 적어줘. 토큰·계좌·긴 로그는 넣지 마.
```

### 리허설 프롬프트 3 · Part 4 KIS 실제 수급 시연 점검

```text

6. 결과에는 데이터 원천, 기준일, 수급 섹션의 전후 차이, simulation, 주문 계열 호출 0회만 짧게 남겨줘.
```

### 선택 준비 · P3-01용 Discord 연결 설정

Discord를 보여 줄 사람만 P3-01 전에 설정한다. Discord 알림은 필수 준비물이 아니다. 강사는 첫 전체 실행에서 실데이터와 함께 보여 주고, 준비된 수강생은 같은 경로를 선택할 수 있다. 준비되지 않은 수강생은 Discord 없이 연습 데이터로 진행한다. 이 알림에는 계좌번호나 잔고가 아니라, 방금 실행한 스크리닝 결과와 AI 판단 근거만 나온다.

1. Discord에서 강의용 서버의 **서버 설정 → 연동 → 웹후크**로 들어간다.
2. **새 웹후크 만들기**를 누르고, 메시지를 받을 비공개 채널을 고른다. 채널 이름은 `#prism-test`처럼 수업 시연용이라는 사실이 드러나게 정한다.
3. **웹후크 URL 복사**를 누른다. 이 주소만 있으면 채널에 메시지를 보낼 수 있으므로, 강의 채팅·슬라이드·화면 공유·Git에 노출하지 않는다.
4. 코딩 에이전트에게 `.env.example`을 로컬 `.env`로 복사하고 운영체제의 기본 텍스트 편집기로 열어 달라고 한다. 강사는 아래 두 줄을 직접 입력·저장한다.

```env
LECTURE_NOTIFY_DISCORD=1
DISCORD_WEBHOOK_URL="복사한 웹후크 주소"
```

5. 웹후크 주소는 코딩 에이전트 채팅에 붙여넣지 않는다. 저장 뒤에는 값 자체를 출력하지 않고 `준비됨 / 비어 있음 / 형식 오류`만 확인한다. `.env`가 Git 추적에서 제외됐는지도 확인하되, `.gitignore`는 Git 업로드를 막을 뿐 에이전트의 로컬 파일 읽기까지 막지는 않는다고 설명한다. 이 설정의 확인은 별도 mock 실행으로 반복하지 않고, 리허설과 수업의 P3-01 `real_data + Discord + simulation` 전체 흐름 한 번에서 끝낸다. 실제 전송 성공 건수·실패 원인과 실제 주문 0건만 기록한다.

**수강생 행동:** 프롬프트 파일에서 [P3-M1](../lecture/exercises/수강생_붙여넣기_프롬프트_파트3.md#p3-m1--screeningpy-구조를-묻고-실행하기)의 코드 블록 전체를 복사해 한 번 붙여넣는다. 원본 PRISM 비교는 시키지 않는다.

**증거 공개:** 연습 종목 7개 가운데 현대차는 등락률이 +4.2%로 가장 높지만 거래량이 평소의 3.6배라 5배 기준을 통과하지 못한다. 삼성전자·SK하이닉스·NAVER 세 종목이 남는다. 많이 오른 종목과 내 규칙을 통과한 종목은 다르다는 예시다.

**60초 짝 대화:** P3-M1 마지막 질문 세 개 중 하나를 골라 자기 전략에 대입해 말한다. 시간이 부족하면 전체 공유는 생략해도 짝 대화는 남긴다.

**수강생 판단 뒤 lecture-prism 기준선**

> 우리 연습 코드는 거래량 5배·시가총액 5,000억·상승 여부를 함께 봅니다. 이 조건을 통과한 종목은 등락률이 높은 순서로 최대 세 종목만 남깁니다. 거래량 기준처럼 전략에 가까운 숫자는 바꿔 볼 수 있지만, 후보 수 제한과 연습 데이터 폴백은 안전장치로 남겨 두는 편이 좋습니다. 수강생의 답이 이 기준과 달라도 오답은 아닙니다. 무엇을 바꿀지 말할 수 있으면 적용이 시작된 것입니다.

## 40–55분 · 모듈 2 — 여섯 에이전트가 근거를 만들고 보고서를 조립한다

**화면:** P3-S15–S22.

**문제 먼저**

> 이 종목을 사기 전에, 어떤 정보까지 확인하고 싶으세요?

**20초 예상:** 실제로 사고 싶은 종목 하나를 떠올리고, 주문 전에 확인하고 싶은 정보 세 가지를 적게 한다.

**그림 출처:** P3-S15는 원본 PRISM의 여섯 분석 방향 그림이다.
P3-S16–S18은 원본 코드와 핵심 프롬프트를 대조해 새로 만든 강의용 보조
그림이며, 화면 속 예시 데이터는 실제 종목 자료가 아니다.

**읽을 말**

> 원본 심층분석은 가격·거래량, 투자자 수급, 기업 현황, 기업 개요, 뉴스, 시장지수의 여섯 방향을 병렬로 읽습니다. 각 에이전트는 같은 질문을 반복하는 것이 아니라 서로 다른 자료와 출력 형식을 맡습니다.
>
> 가격·거래량 에이전트는 수치와 패턴을, 수급 에이전트는 투자주체 흐름을, 기업·뉴스 에이전트는 사건의 맥락을 설명합니다. 그 결과를 투자전략과 요약 보고서로 조립합니다. 이 모듈의 그림 속 차트·기사·숫자는 프롬프트의 역할을 이해시키는 개념 예시이지 실제 종목 데이터가 아닙니다.
>
> 원본 분석 보고서에는 조건부 매수·매도 가격대가 들어갈 수 있습니다. 그러나 그것은 보고서의 전략 초안입니다. CAN SLIM과 최종 Enter/No Entry 판정은 다음 모듈의 매매 시나리오 에이전트가 맡습니다.
>
> 강의용도 `analysis_agents.py`에 기술·수급·재무·산업·뉴스·시장 역할을 각각 정의했습니다. LLM을 연결하면 전문 에이전트 6개가 독립적으로 호출되고, 마지막 편집 에이전트가 일치하는 근거와 충돌하는 근거를 요약합니다. 하나가 실패해도 그 섹션만 규칙 보고서로 돌아갑니다.
>
> `analysis.py`의 `run_analysis_report()`는 여기서 멈춥니다. 결과에는 매수 추천·점수·목표가·손절가가 없습니다. 이 책임은 다음 모듈의 `buy_agent.py`로 넘깁니다.

**수강생 행동:** 프롬프트 파일에서 [P3-M2](../lecture/exercises/수강생_붙여넣기_프롬프트_파트3.md#p3-m2--여섯-보고서-에이전트를-묻고-실행하기)의 코드 블록 전체를 붙여넣는다. P3-M2에서는 Yahoo Finance로 005930 실데이터를 한 번 확인하고, 연결이 막히면 재시도 없이 연습 데이터로 돌아간다. `analysis.py` 단독 실행 뒤 저장된 `reports/`의 Markdown 분석 보고서를 연다. `한눈에 보는 데이터`, 편집장의 `우호적 근거·경계할 근거·다음 확인`, 여섯 섹션의 `핵심 수치·전문 분석가 해석·데이터 한계·확인할 사항`을 순서대로 읽는다. LLM이 연결되지 않아도 이 구조를 갖춘 기본 보고서가 남고, LLM이 연결되면 같은 근거에 대한 전문 분석가 해석이 더 풍부해진다는 점을 짚는다. 뉴스 제목은 `종목 직접 관련 뉴스·주변 산업 뉴스·관련성 불명`으로 나눠 본다. 기사 본문을 실제로 열어 읽지 않았다면 “호재·악재나 실적 영향을 단정하지 마”라고 안내하고, 연결이 불분명한 제목은 `관련성 확인 필요`로 남긴다. 이 시점에는 매수 결론이 아니라 보고서가 근거를 어떻게 조직하는지만 확인한다.

**P3-S22에서 읽을 말**

> 여기서 강의용 시스템의 한계를 분명히 보겠습니다. 지금 보고서는 yfinance 한 곳으로 가격·거래량·기본 재무·지수·뉴스 제목을 빠르게 모읍니다. 전체 흐름을 익히기에는 좋지만, 이 자료만으로 실전 판단을 완성할 수는 없습니다.
>
> 수급은 투자자별 순매수가 아니라 거래량으로 만든 간접 지표입니다. 재무 수치는 어느 분기나 사업연도 기준인지 다시 확인해야 하고, 뉴스는 기사 본문이 아니라 제목만 들어올 수 있습니다. 시장 분석도 국내 지수의 최근 흐름에 가깝기 때문에 환율·금리·해외 동종 업종까지 자동으로 설명하지는 못합니다. 이 빈칸은 LLM을 더 좋은 모델로 바꾼다고 채워지지 않습니다. 없는 근거를 그럴듯하게 말하게 될 위험만 커집니다.
>
> 보완할 때는 데이터를 많이 긁어오는 것부터 시작하지 않습니다. 내 전략에 꼭 필요한 빈칸을 고르고, 그 근거를 가장 잘 주는 출처를 찾습니다. Open API는 HTTP로 정해진 필드를 안정적으로 받고, 웹 크롤링은 API가 없는 공개 문서를 읽고, 파일·DB는 내부 기록을 재사용합니다. MCP는 그 출처를 에이전트가 쓸 수 있게 연결하는 통로이지 데이터 출처 자체는 아닙니다. 공시 사이트, 거래소 자료, 증권사 HTS·MTS, 기업 IR, 뉴스 원문, 거시경제 통계가 후보입니다. 가격·거래량은 기술 섹션, 투자자별 매매는 수급 섹션, 분기 실적과 공시는 재무 섹션, 기업 발표와 기사 원문은 산업·뉴스 섹션, 환율·금리·업종 지수는 시장 섹션에 넣습니다.
>
> 출처 이름만 정해서는 부족합니다. 어떤 필드를 가져올지, 기준 시각과 단위는 무엇인지, 얼마나 자주 갱신할지, 자료가 없으면 멈출지 기존 값으로 돌아갈지까지 정해야 합니다. 마지막에는 데이터를 넣기 전과 뒤에 근거와 판단이 어떻게 달라졌는지 비교합니다.

**증거 공개:** 수급 분석 에이전트만 실패하는 테스트에서도 다른 다섯 보고서는 남고, 실패한 수급 섹션만 규칙 보고서로 대체된다. 편집 에이전트는 남은 결과로 전체 요약을 완성한다. 역할 분리는 관점뿐 아니라 실패 범위도 나눈다.

**60초 데이터 설계:** 방금 연 보고서에서 가장 아쉬운 근거 하나를 고른다. 옆 사람에게 `무슨 자료가 필요한지 → 어디서 구할지 → 어떤 값만 가져올지 → 여섯 섹션 중 어디에 넣을지` 순서로 말한다. 이 시간에는 새 서비스에 가입하거나 연동하지 않는다.

**수강생 판단 뒤 lecture-prism 기준선**

> 현재 코드는 yfinance를 공통 출발점으로 삼습니다. 가격·거래량은 직접 근거에 가깝지만, 수급은 거래량 간접 지표이고 뉴스는 제목 중심이며 재무·시장 자료도 기준 기간과 범위가 제한됩니다. 보완 데이터는 전략마다 다릅니다. 출처를 통째로 붙이지 말고 필요한 필드만 골라 담당 섹션에 넣습니다. 출처·기준 시각·단위·갱신 주기·실패 시 동작을 함께 기록해야 합니다. 여섯 역할은 서로 따로 움직여 하나가 실패해도 그 섹션만 규칙 보고서로 바뀝니다. 근거 전체가 비어 있으면 다음 단계의 매수 에이전트가 PASS로 돌려보내고, 출처가 부족하거나 근거가 충돌하면 No Entry를 선택할 수 있습니다.

## 55–62분 · 연결 실습 — 실제 LLM이 판단에 참여할 수 있는 선을 확인한다

**전환 질문**

> 같은 실데이터를 실제 LLM이 읽으면 무엇이 달라지고, 무엇은 그대로여야 할까요?

**강사 대표 시연:** 강사는 공식 Codex 로그인이 준비된 A 경로를 한 번 보여 준다. `LECTURE_PROFILE=research`, `LECTURE_LLM_MODE=oauth`, `LECTURE_RESEARCH_TOOLS=""`, `LECTURE_NOTIFY_DISCORD=0`, `LECTURE_TRADE_MODE=simulation`으로 삼성전자 005930 한 종목만 실행한다. `codex exec`는 main.py 안의 승인된 외부 실행에서만 사용하고 OAuth 전체 호출은 한 번만 한다. Perplexity·Firecrawl·Discord·브로커는 사용하지 않는다.

**수강생 A/B 분기:** 수강생 프롬프트 파일에서 [P3-M2L](../lecture/exercises/수강생_붙여넣기_프롬프트_파트3.md#p3-m2l--실제-llm을-연결해-판단-경계-확인하기)을 연다.

- **A 경로 · 공식 Codex 로그인이 이미 준비된 사람:** 새 로그인이나 설치 없이 실제 OAuth research 전체 흐름을 한 번 실행한다. 실제 LLM 성공, 섹션별 규칙 폴백, 호출 경로 실패를 구분하고 재시도하지 않는다.
- **B 경로 · 공식 Codex 로그인이 준비되지 않은 사람:** 로그인·설치·네트워크 호출 없이 강사가 저장한 보고서와 증거 메모를 읽는다. 첫 줄에 `이번 실행의 OAuth 호출은 0회`를 표시한다. 증거에 실제 LLM 성공이라고 명시된 경우에만 실제 결과라고 부르고, 증거가 없으면 LLM 결과를 꾸며내지 마라고 안내한 뒤 P3-M2 기본 보고서로 계속한다.

**실패 전환:** A 경로에서 권한·DNS·Yahoo 429·OAuth 오류가 나면 반복 점검이나 새 mock 실행을 하지 않는다. 강사가 준비한 B 경로 결과로 즉시 바꾸고, 선택 연결 실패가 기본 보고서와 다음 매매 규칙을 깨지 않는다는 사실을 보여 준다.

**합류해서 읽을 말**

> 두 경로는 이제 P3-M3으로 합류합니다. 실제 LLM은 근거의 맥락을 더 풍부하게 설명하고, 위험이 크면 BUY를 HOLD로만 낮출 수 있습니다. 점수·목표가·손절가는 규칙이 정합니다. 다음 단계의 `trading.py`는 손익비와 자금 조건을 다시 확인합니다. 어느 경로에서도 실제 주문은 없고 모두 simulation입니다.

**화면에서 비교할 것:** 데이터 원천, 실제 LLM 호출 여부, 성공 섹션과 규칙 폴백 수, 정성 설명, 추천·점수·목표가, HOLD veto, simulation 체결 수만 남긴다. 로그인 화면·토큰·인증 파일·긴 실행 로그는 보여 주지 않는다.

## 62–77분 · 모듈 3 — 진입·증액·청산을 별도 매매 책임으로 둔다

**화면:** P3-S23–S32.

**문제 먼저**

**읽을 말**

> 청산은 순서가 중요합니다. 기계적 손절과 트레일링 스탑을 먼저 확인하고, 그다음 시나리오 판단을 참고합니다. 목표가는 수익을 보장하는 버튼이 아니라 점검할 이정표입니다.
>
> 강의용 `buy_agent.py`가 완성된 보고서를 읽고 Enter / No Entry, 점수, 목표가, 손절가를 포함한 시나리오를 만듭니다. LLM은 규칙 숫자를 바꾸거나 미진입 후보를 억지로 올릴 수 없습니다. 그 뒤 `trading.py`가 가격 배열·손익비·보유 수·현금 한도를 다시 확인하고 수량을 계산합니다.
>
> 자동매매는 장 시작 때 한 번 실행했다고 끝나지 않습니다. `operations.py`가 분석 배치, 보유종목 감시, 미체결 주문 대사를 각각 한 번씩 실행할 수 있게 했습니다. 수업에서는 예약 실행을 켜지 않고, 안전한 일회성 명령만 봅니다.

**수강생 행동:** 프롬프트 파일에서 [P3-M3](../lecture/exercises/수강생_붙여넣기_프롬프트_파트3.md#p3-m3--tradingpy와-운영-루프를-묻고-실행하기)의 코드 블록 전체를 붙여넣는다. 이제 처음으로 `buy_agent.py`의 의견과 `trading.py`의 주문 전 안전 조건을 함께 확인한다.

**증거 공개:** 테스트에서는 BUY 8점이어도 손익비가 1.0이면 주문을 만들지 않는다. HOLD라면 점수가 10점이어도 주문을 만들지 않는다. `trading.py --exit`은 손절·트레일링 스탑·목표가 도달을 서로 다른 청산 결과로 보여 준다.

**내 안전선 한 문장:** 주문 0건을 확인한 뒤 “내 전략에서는 AI가 사라고 해도 ___이면 주문하지 않는다”를 각자 채우게 한다. 두세 명에게 한 문장만 읽어 달라고 한다.

**수강생 판단 뒤 lecture-prism 기준선**

> 우리 코드의 진입 기준은 BUY 의견, 6점 이상, 목표가 > 현재가 > 손절가, 손익비 1.5 이상입니다. 여기에 남은 현금과 자리, 이미 보유한 종목인지, 끝나지 않은 주문이 있는지도 확인합니다. 청산은 손절 → 트레일링 스탑 → 목표가 순서입니다. 체결 상태가 불분명하면 같은 종목의 새 주문을 만들기 전에 `reconcile`로 기존 주문 상태부터 다시 읽습니다.

**안전 확인**

- 모든 체결은 `simulation`
- `operations.py reconcile`은 조회만 하며 주문을 만들지 않음
- 예약 루프는 `LECTURE_ENABLE_SCHEDULER=1` 없이는 시작되지 않음

## 77–90분 · 모듈 4 — 결과를 교훈으로 만들고, 기억을 압축한다

**화면:** P3-S33–S39.

**문제 먼저**

> 어제 손절한 종목이 오늘 다시 떴습니다. 다시 사도 될까요?

**20초 예상:** `바로 다시 산다 / 하루 더 본다 / 조건을 다시 확인한다` 중 하나를 고르고 이유를 한 문장으로 적게 한다.

**그림 출처:** P3-S33은 원본 PRISM의 매매일지·교훈·재진입 흐름이다.
P3-S35은 실제 서버의 압축 배치와 Lecture-prism의 메모리 계층을 함께
설명하기 위해 새로 만든 보조 그림이다.

**읽을 말**

> 매수 직후에는 아직 성공도 실패도 알 수 없습니다. 그래서 강의용 피드백은 BUY 기록만으로 억지 교훈을 만들지 않습니다. SELL로 결과가 닫혔을 때 분석과 체결을 연결해 교훈을 남깁니다.
>
> 교훈을 계속 쌓기만 하면 프롬프트가 길어지고 오래된 예외가 판단을 방해합니다. `memory.py`는 최근 교훈을 단기 기억으로 두고, 시간이 지난 교훈을 중기로 옮기며, 반복된 패턴만 장기로 승격합니다. 장기 기억도 개수를 제한합니다.
>
> 실제 운영 서버에서는 한국 시장 분석이 평일 오전 9시 30분과 오후 2시 46분에 돌고, 메모리 압축은 일요일 새벽 3시에 실행됩니다. 강의용은 이 아이디어를 표준 라이브러리와 SQLite만으로 작게 재현했습니다.
>
> 기억은 많이 쌓는 것보다 쓸 만하게 유지하는 게 중요합니다. 같은 종목의 최근 교훈은 먼저 참고하고, 서로 다른 거래에서 반복된 교훈만 장기 원칙으로 압축합니다. 오래된 기록은 중기 요약으로 옮기고, 한도를 넘는 약한 장기 원칙은 다음 판단에서 빼둡니다.

**수강생 행동:** 프롬프트 파일에서 [P3-M4](../lecture/exercises/수강생_붙여넣기_프롬프트_파트3.md#p3-m4--피드백과-메모리-압축을-묻고-실행하기)의 코드 블록 전체를 붙여넣는다. 거래 결과가 닫힌 뒤의 기록과 압축만 확인한다.

**증거 공개:** BUY 체결은 거래 기록만 남기고 결과 교훈을 만들지 않는다. SELL로 거래가 끝나야 단기 교훈이 생긴다. 서로 다른 두 종목에서 같은 교훈이 반복되면 하나의 장기 원칙으로 압축한다.

**재진입 선택 공유:** 세 선택지별로 한 명씩 이유를 읽게 한다. 그다음 P3-M4 마지막 질문 가운데 반복 실수 기준이나 버릴 일회성 상황 하나를 자기 전략에 대입해 적게 한다.

**수강생 판단 뒤 lecture-prism 기준선**

> 강의용 구현은 BUY 직후에는 교훈을 만들지 않고 SELL로 거래가 닫힌 뒤 단기 교훈을 남깁니다. 같은 실행에서 방금 청산한 종목은 다시 사지 않지만, 어제 손절했다는 이유만으로 다음 날 자동으로 매수를 막는 규칙은 아직 없습니다. 단기 교훈은 7일이 지나면 중기로 옮기고, 30일이 지난 중기 교훈 가운데 같은 내용이 두 번 이상 반복될 때 장기 원칙으로 만듭니다. 장기 원칙은 최대 20개만 유지하고 다음 판단에는 관련 기억을 최대 5개만 넣습니다. 다만 아직 처음 계획과 실제 수익률과 청산 사유까지 깊게 비교하지는 않습니다. 일회성 상황을 뜻으로 판별하는 기능도 없습니다. 이 질문들은 현재 기능을 외우라는 뜻이 아니라, 수강생이 다음에 보완할 기준을 정해 보라는 질문입니다.

## 90분 전후 · 모듈 5 — 내 컴퓨터의 운영 준비 상태 확인하기

**화면:** P3-S40–S41.

**문제 먼저**

> 여기까지는 프로그램을 한 번 실행해 봤습니다. 내일도, 모레도 안전하게 돌리려면 `main.py`만 계속 켜 두면 될까요?

**20초 예상:** `충분하다 / 부족하다 / 아직 모르겠다` 중 하나를 고르게 하고, 이유를 짧게 말하게 한다.

**읽을 말**

> `main.py`를 켜 둔다고 운영이 되는 것은 아닙니다. 이 파일은 후보를 찾고, 분석하고, 매매 여부를 판단하고, 기록을 남기는 일을 한 번 수행합니다. 매일 운영하려면 다음 실행을 시작하는 일과 실행 뒤 상태를 확인하는 일도 따로 챙겨야 합니다.
>
> 컴퓨터가 맡을 일은 다섯 가지입니다. 정해진 때 시작하고, 보유 종목을 살피고, 주문 결과를 확인하고, 기록을 정리하고, 이상이 생기면 사람에게 알려 줍니다. 어려운 이름을 외울 필요는 없습니다. 언제 시작했고, 무엇을 확인했으며, 어디에서 멈췄는지만 알면 됩니다.
>
> 이제 수강생이 컴퓨터에서 무엇을 실행하는지 보겠습니다. 수강생은 터미널 명령어를 직접 입력하지 않습니다. P3-M5를 코딩 에이전트에 붙여넣으면 에이전트가 `operations.py doctor`로 준비 상태 점검(doctor)을 하고, `operations.py status`로 현재 상태를 읽습니다. 결과는 준비됨(configured)과 준비 안 됨(missing)으로만 보여 줍니다. 비밀값은 보여 주지 않습니다.
>
> 여기에는 서로 다른 두 기준이 있습니다. `doctor → simulation → paper → live`는 안전 점검 순서입니다. `doctor`는 준비 상태를 확인하고, `simulation`은 주문을 보내지 않는 실행 방식입니다. 반면 연습 데이터(mock), 실데이터와 분석 보강(real_data, research)은 어떤 자료와 분석 기능을 쓸지 정하는 이름입니다. 실데이터를 읽는다고 실제 주문이 나가는 것은 아닙니다. 실거래에는 `LECTURE_ENABLE_LIVE_BROKER`와 `LECTURE_ALLOW_REAL_BROKER`라는 두 잠금장치가 더 남아 있습니다.
>
> 정해진 시각에 자동으로 시작하는 기능은 오늘 켜지 않습니다. 실제 운영에서는 예약 정보(`operations.py schedule`)와 컴퓨터의 자동 실행 관리 기능인 서비스 관리자(service manager)가 함께 필요합니다.
>
> 증권사 연결도 따로 봅니다. KIS는 강의에서 가장 많이 확인한 기준선입니다. Kiwoom은 조건부 연결이므로 일부 기능을 더 확인해야 합니다. Toss는 공식 Open API와 WTS를 분리해서 봐야 합니다. 공식 Open API에는 모의투자 환경이 없고, WTS만 연결됐다고 실거래 준비가 끝난 것은 아닙니다. 기술 문서에서 쓰는 준비됨(READY)은 바로 확인할 수 있다는 뜻이고, 추가 확인 필요(CONDITIONAL)는 아직 점검할 항목이 남았다는 뜻입니다.

**강사 메모:** 다섯 작업의 기술 이름은 전체 배치, 보유 감시, 주문 대사, 기억 압축, 상태·알림이다. 서비스 관리자는 macOS의 launchd, Linux의 systemd, Windows의 작업 스케줄러를 뜻한다. 수업에서는 이름을 외우게 하지 않는다.

**수강생 행동:** 프롬프트 파일에서 [P3-M5](../lecture/exercises/수강생_붙여넣기_프롬프트_파트3.md#p3-m5--내-컴퓨터의-운영-준비-상태-확인하기)의 첫 번째 블록을 코딩 에이전트에 붙여넣는다. 에이전트가 준비 상태를 읽으면 `준비됨 / 준비 안 됨` 표에서 지금 가능한 단계와 다음에 채울 한 가지를 찾게 한다. 시간이 남으면 두 번째 블록으로 다음에 준비할 단계 하나만 고른다.

**안전 확인**

- 시크릿 값은 출력하지 않음
- 서비스 등록·시작·중지·재시작 없음
- `LECTURE_ENABLE_LIVE_BROKER`, `LECTURE_ALLOW_REAL_BROKER`를 포함한 플래그 변경 없음
- 실제 주문·취소·정정 없음
- 결과는 준비됨(configured) / 준비 안 됨(missing)으로만 보고함

**수강생 판단 뒤 lecture-prism 기준선**

> `main.py`는 판단 흐름을 한 번 실행합니다. 매일 운영하려면 전체 배치, 보유 감시, 주문 대사, 기억 압축, 상태·알림을 나눠 챙겨야 합니다. 수강생은 P3-M5를 코딩 에이전트에 붙여넣고 `operations.py doctor`와 `operations.py status` 결과만 읽습니다. 준비 순서는 `doctor → simulation → paper → live`이며, 프로필 이름은 `mock`, `real_data`, `research`, `paper`, `live`입니다. 자동 실행은 `operations.py schedule`과 서비스 관리자(service manager)가 맡지만 수업에서는 켜지 않습니다. KIS는 기준선, Kiwoom은 추가 확인이 필요한 조건부 연결, Toss는 공식 Open API와 WTS를 나눠 봅니다. 실제 주문 전에는 두 잠금장치 `LECTURE_ENABLE_LIVE_BROKER`, `LECTURE_ALLOW_REAL_BROKER`, 사람의 승인, 별도 실계좌 전체 확인(E2E)이 남습니다.

## 22–32분 · P4-02: 에이전트·도구·통신 원리를 읽는다

**읽을 말**

**성공 증거:** 수강생이 “앞 에이전트의 무엇이 다음 에이전트의 입력이 되는지” 한 사례를 말할 수 있다.

- 수집 건수·제외 이유·검토 대기·LLM에 넘긴 자료 수
- 최종 최대 3건의 출처·날짜·핵심 주장과 길이 제한

**이 구간의 완료 기준:** 강사는 D1~D4를 `완료 / 폴백으로 검증 / 다음 작업`으로 구분해 보여준다. 수강생은 `PRD → 작업·검증 계획 → 설계 → 구현 → 검증 → 피드백` 기록과 `원한 변화 → 바꾼 파일과 규칙 → 수정 전후 결과 → 확인한 증거`를 연결한다. 결과가 아직 없으면 성공 사례를 꾸미지 않고 계획·진행 상태만 표시한다.

## 88–96분 · P4-09: 로그로 원인을 좁혀 디버깅한다

**화면:** P4-S39–S42.

**읽을 말**

> 디버깅은 오류 문장을 없애는 일이 아닙니다. 같은 조건에서 다시 재현하고, 처음 깨진 위치를 찾고, 원인 가설을 하나 확인한 다음, 가장 작은 부분만 고치는 일입니다.
>
> 로그는 프로그램의 작업 일지입니다. 시각, 실행 단계, 입력, 데이터 원천, 성공·실패·폴백을 읽으면 어디까지 정상적으로 움직였는지 알 수 있습니다.

**수강생 행동:** 실제 오류가 있는 사람은 [P4-09](../lecture/exercises/수강생_붙여넣기_프롬프트_파트4.md#p4-09--로그로-원인을-좁혀-디버깅하기)를 사용한다. 오류가 없는 사람은 방금 실행 로그에서 경고 하나를 골라 실패인지 정상 폴백인지 설명하게 한다.

**성공 증거:** 재현 조건, 처음 실패한 위치, 원인, 최소 수정 또는 ‘수정 불필요’, 회귀 확인이 구분돼 있다.

## 96–103분 · P4-10: DB와 테이블에서 결과를 찾는다

**화면:** P4-S43–S44.

**읽을 말**

> DB는 실행 결과를 다시 꺼내 쓰기 위한 저장소이고, 테이블은 같은 종류의 기록을 행과 열로 모은 표입니다. 대시보드의 숫자도 DB에 저장된 기록을 읽어 온 결과입니다.

**수강생 행동:** [P4-10](../lecture/exercises/수강생_붙여넣기_프롬프트_파트4.md#p4-10--db와-테이블에서-실행-기록-확인하기)을 실행한다. SQL을 직접 입력하지 않고, 에이전트가 `db.py`와 SQLite 스키마를 읽기 전용으로 조사한 뒤 최근 기록을 표로 보여주게 한다.

**확인 질문:** “방금 실행의 시각과 결과는 어느 테이블의 어떤 열에 남았나요?”

**성공 증거:** 테이블 이름, 한 행의 의미, 최근 실행 시각, 대시보드가 읽는 기록이 연결돼 있다.

## 103–117분 · P4-11~P4-13: 3분 뒤 로컬 예약 실행을 확인하고 지운다

**화면:** P4-S45–S50.

**읽을 말**

> 배치는 정해진 일을 한 묶음으로 실행하는 것이고, 스케줄러는 그 일을 언제 시작할지 정합니다. 오늘은 서버에 배포하지 않습니다. 각자 자기 컴퓨터에서 3분 뒤 한 번 실행되는 예약을 만들어 원리를 확인합니다.
>
> 서버는 계속 켜 둘 수 있는 다른 컴퓨터입니다. 안정적인 예약 실행에는 유리하지만 비용·보안·배포·모니터링이 더 필요합니다. 오늘은 그 차이까지만 이해합니다.

**1단계 · 설계:** [P4-11](../lecture/exercises/수강생_붙여넣기_프롬프트_파트4.md#p4-11--3분-뒤-로컬-예약-실행-설계하기)을 실행한다. 에이전트가 운영체제를 확인하고, 실행 시각·Python과 프로젝트 절대 경로·mock·simulation·로그 파일·중지와 삭제 방법을 먼저 보여준다. 이 단계에서는 예약을 만들지 않는다.

**2단계 · 승인 후 등록:** 수강생이 변경 목록을 읽은 뒤에만 [P4-12](../lecture/exercises/수강생_붙여넣기_프롬프트_파트4.md#p4-12--승인-후-예약하고-증거-확인하기)를 실행한다. 예약 항목과 실행 시각을 확인하고 3분을 기다린다.

**기다리는 3분:** 강사는 오전·오후 실행, 휴장일, 절전, 중복 실행 방지를 설명한다. 예약을 다시 만들거나 여러 번 실행하지 않는다.

**3단계 · 증거 확인과 삭제:** 로그에서 다섯 단계 완료와 mock·simulation을 찾고, DB의 최신 시각이 새로 생겼는지 확인한다. 이어서 [P4-13](../lecture/exercises/수강생_붙여넣기_프롬프트_파트4.md#p4-13--임시-예약-삭제하고-반복-주기-설계하기)으로 임시 예약을 삭제하고 예약 목록에서 사라졌는지 확인한다.

**실패 전환:** 3분 뒤 실행되지 않았다면 새 예약을 만들지 않는다. 컴퓨터 절전, 경로, Python 실행 파일, 권한, 로그 파일 존재 여부를 P4-09 방식으로 확인한다. 수업 종료 전에는 임시 예약을 반드시 삭제하거나, 삭제되지 않은 수강생을 강사가 따로 확인한다.
