# lecture-prism 실운영 런타임과 파트 3 운영 안내 설계

## 목표

`lecture-prism`을 한 번 실행하는 강의 예제에 머물지 않고, 한국 주식 시장에서 반복 운영할 수 있는 시스템으로 보강한다. 파트 3 막판에는 수강생이 지금까지 배운 옵션을 한눈에 정리하고, 자기 컴퓨터나 서버에서 어떤 프로필과 안전 플래그를 선택하며 어떤 프로세스를 계속 살려 두어야 하는지 설명할 수 있어야 한다.

실전투입 가능하다는 말은 실제 수익을 보장한다는 뜻이 아니다. 이 설계에서 뜻하는 실운영 준비는 다음과 같다.

- 컴퓨터가 재시작되어도 운영 프로세스가 다시 시작된다.
- 같은 작업이 겹쳐 실행되지 않는다.
- 휴장일과 장 시간을 확인하고, 오래됐거나 출처가 불분명한 가격으로 주문하지 않는다.
- 주문 접수·부분 체결·체결·취소·결과 불명을 서로 다르게 기록한다.
- 결과 불명 주문이 있으면 같은 종목의 새 주문을 막고 대사부터 한다.
- 실행 로그와 마지막 정상 동작 시각을 남기고, 실패를 알림으로 보낸다.
- 실전 주문은 기존 이중 안전 플래그와 별도의 무인운영 승인을 모두 통과해야 한다.

## 현재 상태에서 확인된 부족한 점

현재 `operations.py schedule`은 `LECTURE_ENABLE_SCHEDULER=1`일 때 계속 실행되지만, 예약 배치와 보유종목 감시는 모두 `dry_run=True`로 고정되어 있다. 따라서 `.env`를 `paper`나 `live`로 바꿔도 예약 실행은 증권사 주문을 보내지 않는다.

추가로 다음 항목이 실운영 기준에 미치지 못한다.

- 스케줄러가 여러 개 뜨는 것을 막는 단일 인스턴스 잠금이 없다.
- 컴퓨터 재시작 뒤 자동 복구는 운영체제 서비스 관리자에게 맡겨야 하지만 배포 예제가 없다.
- 평일만 구분하고 한국 시장 휴장일을 확인하지 않는다.
- 보유종목 감시가 하루 한 번뿐이며, 청산 가격은 브로커 시세가 아니라 공용 데이터 경로를 다시 읽는다.
- 스케줄러 로그가 파일로 남지 않고 마지막 성공·실패 상태를 조회할 명령도 없다.
- 키움 어댑터는 주문 제출까지만 있고 주문 상태 조회·취소·재시작 대사가 없다.
- 토스는 비공식 WTS 세션을 사용하고 모의투자 환경이 없으므로 KIS와 같은 실운영 준비 완료로 볼 수 없다.
- KIS와 토스의 주문 수명주기는 fixture로 폭넓게 검증됐지만 실제 계좌 주문 E2E는 수행하지 않았다.

## 운영 단계

수강생에게는 옵션을 낱개 스위치가 아니라 네 단계로 설명한다.

| 단계 | 대표 프로필 | 데이터·분석 | 주문 | 사용 목적 |
| --- | --- | --- | --- | --- |
| 연습 | `mock` | 연습 데이터·규칙 보고서 | simulation | 설치와 전체 흐름 확인 |
| 관찰 | `research` | yfinance·LLM·선택 리서치 도구 | simulation | 실데이터 보고서와 알림 운영 |
| 모의 운영 | `paper` | 실데이터·research | 증권사 demo | 주문 수명주기와 재시작 복구 검증 |
| 실전 운영 | `live` | 실데이터·research | 증권사 real | 검증을 마친 전략의 실제 계좌 운영 |

공통으로 Discord 알림과 운영 스케줄러를 선택할 수 있다. `paper`와 `live`는 외부 데이터 실패를 연습 데이터 주문으로 바꾸지 않고 멈춘다.

## 런타임 구조

### 1. 프로필을 따르는 예약 실행

`operations.py`의 배치와 감시가 현재 런타임 프로필을 읽도록 바꾼다.

- `mock`, `classroom`, `real_data`, `research`, `backtest`는 항상 simulation이다.
- `paper`와 `live`도 기본 실행은 simulation으로 남긴다.
- 증권사 주문까지 허용하려면 서비스 시작 명령에 `--execute-broker`가 있어야 한다.
- `--execute-broker`가 있어도 기존 `LECTURE_ENABLE_LIVE_BROKER=1`이 없으면 demo와 real 모두 차단한다.
- real 모드는 `LECTURE_ALLOW_REAL_BROKER=1`과 `LECTURE_UNATTENDED_LIVE_ACK=I_ACCEPT_REAL_ORDERS`까지 있어야 한다.

이렇게 수업 중 실수, `.env` 오입력, 무인운영 오설정을 서로 다른 게이트로 막는다.

### 2. 운영 작업

상시 프로세스는 `operations.py schedule` 하나다. `main.py`를 24시간 켜 두지 않는다. 스케줄러가 다음 작업을 새로 시작한다.

- 오전·오후 전체 분석 배치
- 장중 보유종목 감시
- 끝나지 않은 주문 대사
- 주간 메모리 압축
- 운영 상태 기록과 실패 알림

장중 감시와 주문 대사는 하루 한 번이 아니라 설정한 간격으로 실행한다. 이전 작업이 끝나지 않았으면 다음 실행은 건너뛰고 그 사실을 기록한다.

### 3. 단일 인스턴스와 재시작

표준 라이브러리만 사용해 운영 잠금과 상태 파일을 만든다.

- 스케줄러 시작 시 프로젝트별 잠금을 획득한다.
- 이미 살아 있는 스케줄러가 있으면 두 번째 프로세스는 주문 작업을 시작하지 않는다.
- 비정상 종료 뒤 남은 잠금은 PID와 갱신 시각을 확인해 안전하게 회수한다.
- SIGINT·SIGTERM을 받으면 새 작업을 받지 않고 현재 상태를 기록한 뒤 종료한다.

재부팅 자동 시작과 프로세스 재시작은 운영체제 서비스 관리자가 맡는다. 저장소에는 비밀값이 없는 macOS `launchd`, Linux `systemd`, Windows 작업 스케줄러용 예제를 둔다. 수강생은 코딩 에이전트가 자기 운영체제에 맞는 파일을 복사·검토하게 하며 수업 중 자동 등록하지 않는다.

### 4. 장 시간과 가격 신선도

모든 운영 시각은 `Asia/Seoul`을 기준으로 계산한다. KIS 운영은 공식 휴장일 조회를 통과한 날에만 신규 진입 배치를 실행한다.

실전 청산에는 yfinance 종가성 자료를 사용하지 않는다. 브로커 어댑터에 현재가 조회 계약을 추가하고 다음을 검증한다.

- 가격의 종목, 시장, 통화
- 조회 시각과 최대 허용 지연
- 0·음수·소수점이 잘못된 국내주식 가격
- 가격 조회 실패 시 주문 보류

브로커가 신선한 현재가를 제공하지 못하면 `paper/live`의 감시 작업은 청산 주문을 만들지 않고 장애를 알린다.

### 5. 로그·상태·알림

`operations.py`는 날짜별 회전 로그를 `logs/`에 남긴다. `operations.py status`는 시크릿을 읽거나 출력하지 않고 다음만 보여 준다.

- 프로필과 브로커·계좌 모드
- 스케줄러 PID와 마지막 heartbeat
- 마지막 작업별 시작·종료·성공·실패 시각
- 미해결 주문 수
- 마지막 데이터 기준 시각
- 다음 예약 작업

시작, 정상 종료, 작업 실패, 데이터 노후, 대사 불가, 무인운영 게이트 차단을 Discord에 보낸다. 계좌번호·잔고·토큰·웹후크 주소는 메시지에 넣지 않는다.

## 운영 준비도 점검

`operations.py doctor`를 추가한다. 이 명령은 기본적으로 읽기 전용이며 주문을 보내지 않는다.

공통 점검:

- Python과 필수 파일
- `.env` 프로필과 옵션 조합
- 로그·DB·상태 디렉터리 쓰기 가능 여부
- 시스템 시간대
- 데이터·LLM·리서치·Discord 준비 여부
- 단일 인스턴스 잠금과 서비스 관리자 설정
- 실전 게이트가 의도한 값인지

브로커 점검:

- KIS: demo/real 호스트 분리, 인증, 휴장일, 계좌·주문가능수량·보유수량·현재가·미체결 조회를 읽기 전용으로 확인
- 키움: 공식 demo/real 호스트와 토큰·현재가·계좌·주문 상태·취소 계약을 구현한 뒤 읽기 전용 점검
- 토스: `tossctl` 버전, 로그인 세션 만료, 계좌·보유·미체결 조회만 확인. 모의투자 부재와 비공식 연동 경고를 항상 표시

doctor 결과는 `READY`, `CONDITIONAL`, `BLOCKED`로 나눈다. `READY`는 해당 단계의 자동 주문을 기술적으로 시작할 준비가 됐다는 뜻이며 투자 성과를 보장하지 않는다.

## 브로커별 완료 기준

### KIS

KIS를 1차 실운영 기준선으로 삼는다.

- 공식 문서에 맞춘 인증·현재가·휴장일·잔고·주문가능수량·주문·체결조회·취소
- 접수 후 즉시 체결로 간주하지 않음
- 부분 체결과 결과 불명을 원장에 보존
- 재시작 뒤 대사
- 신규 진입과 청산 모두 같은 수명주기 사용
- demo 읽기 전용 연결 점검
- 실제 주문 E2E는 사용자 별도 승인 없이는 실행하지 않음

### 키움

현재 주문 제출 전용 어댑터를 운영 가능한 계약으로 넓힌다.

- 공식 문서 기준 현재가·계좌·주문 상태·취소 구현
- KIS와 같은 원장·결과 불명·재시작 대사 경계 적용
- mock API 인증과 읽기 전용 조회가 가능하면 실제 sandbox로 검증
- 키나 계정이 없으면 공식 요청·응답 fixture와 실패 경계까지만 검증

### 토스

토스는 최대한 검증하되 `READY` 판정을 내리지 않는다.

- 고정 버전 `tossctl` 계약과 fixture 회귀 테스트
- 사용자가 이미 로그인한 경우에만 인증·계좌·보유·미체결 읽기 점검
- 모의투자 환경이 없으므로 자동 주문 검증은 수행하지 않음
- 세션 만료, JSON 형식 변화, 결과 불명 시 즉시 차단
- 운영 문서에 비공식 WTS 의존성과 복구 책임을 명시

## 파트 3 수업 설계

모듈 4 뒤, 파트 3 마지막 적용 전에 `P3-M5 · 내 컴퓨터에서 full 운영 준비하기`를 넣는다.

### 슬라이드

기존 P3-S39 보조 운영 그림 다음에 두 장을 추가한다.

1. `24시간 운영은 한 프로그램이 아니라 다섯 작업을 지키는 일입니다`
   - 운영체제 서비스 관리자
   - `operations.py schedule`
   - 전체 배치, 보유 감시, 주문 대사, 기억 압축, 상태·알림
2. `내가 켤 옵션은 운영 단계에 따라 달라집니다`
   - mock / research / paper / live 사다리
   - 공통 옵션과 paper/live 추가 게이트
   - KIS 기준선, 키움 조건부, 토스 실험적 경계

기존 마지막 적용 슬라이드는 뒤로 이동한다.

### 강사용 답변

강사는 다음 순서로 답한다.

1. `main.py`를 계속 켜 두는 것이 아니라고 바로잡는다.
2. 수강생이 원하는 단계를 mock·research·paper·live 중에서 고르게 한다.
3. 그 단계의 `.env` 옵션과 계속 살아 있어야 하는 스케줄러를 보여 준다.
4. 운영체제 서비스 관리자가 재부팅과 비정상 종료를 복구한다고 설명한다.
5. `doctor → simulation 예행 실행 → paper → live` 순서를 건너뛰지 않는다.
6. 실제 주문 완료가 아니라 접수·부분 체결·체결·결과 불명을 구분해야 운영이라고 설명한다.

### 수강생 붙여넣기 프롬프트

P3-M5는 두 단계다.

- 1단계는 읽기 전용 준비도 감사다. 코딩 에이전트가 운영체제, 현재 프로필, 선택 브로커, 데이터·LLM·알림·스케줄러·서비스 관리자 준비 상태를 표로 보여 준다.
- 2단계는 수강생이 고른 목표 단계의 실행계획을 만든다. 실제 예약 등록과 실전 플래그 변경은 하지 않는다.

프롬프트는 시크릿 값을 읽거나 출력하지 않고 `설정됨/없음`만 표시한다. 실전 단계는 KIS doctor가 통과하고 paper에서 주문 수명주기와 재시작 대사를 확인하기 전까지 `BLOCKED`로 표시한다.

## 검증 계획

### 자동 테스트

- mock/research는 예약 실행에서도 항상 simulation
- paper/live는 `--execute-broker` 없이 simulation
- demo는 broker enable 플래그, real은 enable + allow + unattended ACK가 모두 필요
- 중복 스케줄러와 겹친 작업 차단
- KST 시각, 주말·휴장일, 장전·장후 동작
- 오래된 가격과 조회 실패의 fail-closed
- heartbeat와 상태 파일의 원자적 갱신
- SIGTERM 정상 종료와 재시작
- 로그·Discord의 시크릿 비노출
- KIS/키움/토스별 doctor 판정
- 각 브로커의 접수·부분 체결·체결·취소·UNKNOWN·재시작 대사
- 기존 API 키 없는 `python3 main.py` 완주와 실거래 기본 차단 회귀

### 외부 검증

- 공식 KIS·키움 문서와 구현 필드 재대조
- 사용 가능한 demo 인증이 있으면 인증·휴장일·현재가·잔고·미체결을 읽기 전용으로 확인
- 실제 주문은 사용자에게 주문 종목·수량·가격·계좌 모드가 보이는 별도 승인 없이는 실행하지 않음
- 토스는 세션과 읽기 조회까지만 확인하며 실제 주문을 검증하지 않음

### 강의 자료 검증

- 파트 3 슬라이드 전체 1280×720 렌더링에서 overflow·깨진 이미지 0건
- 슬라이드, 강사 스크립트, P3-M5 프롬프트가 같은 옵션 이름과 운영 경계를 사용
- 수강생이 터미널 명령을 직접 입력하지 않고 코딩 에이전트에게 점검·설계를 맡김
- “fully 돌리면 바로 실계좌 주문 가능”과 “현재 코드·fixture 검증 완료”를 혼동하지 않음

## 제외 범위

- 투자 성과나 수익률 보장
- 사용자 승인 없는 실제 계좌 주문
- 토스 비공식 WTS를 KIS와 같은 운영 준비 완료로 표기
- Kubernetes, Redis, GCP 같은 대규모 인프라 도입
- 수업 중 운영체제 서비스 자동 등록
- 시크릿을 Git, 보고서, 로그, Discord에 저장

## 완료 기준

- KIS 기준으로 research simulation과 paper/live 운영 경로가 같은 스케줄러·원장·대사 구조를 사용한다.
- 운영 프로세스가 재시작 가능하고 중복 실행을 차단하며 상태를 조회할 수 있다.
- paper/live에서 오래된 가격, 휴장일, 인증·조회 실패, 결과 불명 주문은 신규 주문으로 이어지지 않는다.
- 키움은 주문 수명주기와 대사까지 구현되거나 doctor가 미완료 기능을 `BLOCKED`로 표시한다.
- 토스는 읽기 전용 준비 상태를 점검하되 실운영 `READY`로 분류하지 않는다.
- 파트 3 막판의 슬라이드·강사 스크립트·수강생 프롬프트만 읽어도 운영 단계, 옵션, 상시 프로세스, 검증 순서를 설명할 수 있다.
