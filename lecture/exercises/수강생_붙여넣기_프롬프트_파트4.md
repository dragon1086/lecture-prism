### 실행 전 예상

- KIS를 붙여도 가격·기술·재무·뉴스 섹션은 그대로 남을까?

### 코딩 에이전트에 붙여넣기

```text

Part 3 P3-04에서 확인한 [paper 또는 real] 환경을 그대로 사용하고, 어느 환경인지 불분명하면 실행 전에 그 선택만 나에게 물어봐. 키·토큰 값은 읽어서 답변에 출력하거나 복사하지 마.

삼성전자 005930의 기본 yfinance 분석과 KIS 수급 보강 분석을 각각 한 번 비교해줘. KIS 보강은 이번 실행에만 LECTURE_SUPPLY_SOURCE=kis로 적용하고 .env나 플래그 기본값은 바꾸지 마. 매매는 simulation으로 유지해.

결과에는 ① KIS paper/real 환경 ② 실제 데이터 기준일 ③ 가격 ④ 기관·외국인·개인 순매수 ⑤ 보강 전후 달라진 수급 섹션 ⑥ 그대로인 다른 분석 섹션 ⑦ 주문·취소·정정·잔고·계좌 호출 0회를 보여줘. 주말·휴장일이면 실시간이라고 부르지 말고 가장 최근 영업일 기준이라고 적어.

KIS 조회가 실패하면 자동으로 다시 시도하거나 paper/real 환경을 바꾸지 마. 실패 원인을 한 번 기록하고, 분석이 거래량 프록시로 돌아갔다면 그것을 실제 KIS 성공처럼 말하지 마. 코드는 수정하지 마.
```

- 매매 모드는 `simulation`, 주문 계열 호출은 0회임

## P4-08 · 오전 1회·오후 1회 연습 배치 설계하기

> 이 번호는 ‘컴퓨터를 계속 켜 두고, 정해진 시각에 기본 연습 실행을 다시 시작하는 법’을 이해하는 운영 실습입니다. `main.py`가 24시간 떠 있는 것이 아니라, 운영체제의 예약 기능이 오전과 오후에 한 번씩 실행을 시작합니다.

### 실행 전 예상

- 한 번 실행, 배치, 스케줄, 대시보드는 무엇이 다를까?
- 예약이 겹치거나 컴퓨터가 꺼져 있으면 어떤 증거를 남겨야 할까?

### 코딩 에이전트에 붙여넣기 — 1단계: 설계만

```text
lecture-prism을 계속 켜 둔 내 컴퓨터에서 오전 1회, 오후 1회 안전하게 실행하는 연습 운영을 설계해줘.

먼저 내 운영체제와 현재 프로젝트의 실제 실행 시작점(main.py), 기본 연습 데이터와 실제 주문 없는 예행 실행 경로, 보고서·로그·DB 위치를 조사해줘.
한 번 실행 / 배치 / 스케줄 / 대시보드 / 서버의 차이를 초보자 표로 설명해줘.
오전 시각은 [예: 09:10], 오후 시각은 [예: 15:30]으로 가정하되, 시간대와 휴장일을 어떻게 다룰지 함께 제안해줘.
예약이 겹칠 때의 방지 방법, 실패 로그 위치, 예약 중지 방법, 컴퓨터 재시작 뒤 확인 방법을 포함한 계획을 만들어줘.
실행 계획에는 연습 데이터와 실제 주문 없는 예행 실행을 명시해야 하며, 실제 주문·브로커·계좌·시크릿·.env는 절대 읽거나 바꾸거나 등록하지 마.
아직 예약 작업을 만들거나 등록하지 말고, 내가 확인할 체크리스트와 되돌리는 방법만 보여줘.
```

### 성공 증거

- 오전·오후 실행 시각과 시간대가 계획에 있음
- 예행 실행 방식, 로그 위치, 중지·되돌림 방법이 한 표에 있음
- 실제 예약 작업이나 운영체제 설정을 아직 바꾸지 않았다는 확인이 있음

### 실행 후 한 문장

> 내 시스템은 ___가 계속 켜져 있고, ___가 오전과 오후에 ___을 다시 시작한다.

> 실제 예약 등록은 수업 기본 실습이 아닙니다. 수업이 끝난 뒤 운영체제 설정 변경을 이해하고 명시적으로 선택한 경우에만 별도 O-01을 사용합니다.

## P4-11 · 오전 관찰과 오후 확인을 분리하는 전략 예시

> 강사 확장 예시입니다. 지금 코드에 시간대 기능이 없을 수 있습니다. 먼저 설계와 테스트를 만들고, 수강생 기본 실습에서는 연습 데이터와 실제 주문 없는 예행 실행만 사용합니다.

### 실행 전 예상

- 오전의 거래량과 일봉이 아직 완성되지 않았는데, 오후 종가 기준 결론을 내리면 어떤 문제가 생길까?

### 코딩 에이전트에 붙여넣기

```text
lecture-prism을 오전 1회, 오후 1회 실행하는 연습 운영으로 확장하는 설계를 만들어줘.

먼저 main.py의 실행 시작점, 현재 예약 초안, data_source.py, screening.py, analysis.py를 조사해 시간대 구분이 이미 있는지 확인해줘.
없다면 morning/afternoon 실행 창과 기준 시각을 시스템 시간이 아니라 테스트 가능한 입력으로 받는 최소 설계를 제안해줘.

반드시 지킬 규칙:
1. morning에서는 오늘 일봉·거래량이 미완성일 수 있음을 로그와 결과에 표시하고, 이를 종가 확정값처럼 사용해 BUY 결론을 강화하지 않는다.
2. afternoon에서도 데이터 원천·기준 시각·일봉 확정 여부를 확인하고, 확정할 수 없으면 HOLD 또는 다음 실행으로 미룬다.
3. 오전·오후 검증용 예시를 만들어 미완성 데이터를 종가로 오해하지 않는 테스트를 먼저 제안한다.
4. LLM은 시간대 차이를 설명하거나 HOLD를 제안할 수만 있다. 정량 점수·목표가·손절가·실거래 안전장치는 바꾸지 않는다.
5. run_screening, run_analysis, run_trading, run_feedback의 입출력과 기본 mock 경로는 유지한다.
6. 실제 주문·브로커·계좌·시크릿은 절대 사용하지 않는다.

먼저 설계와 테스트 계획만 보여줘. 내가 승인하기 전에는 코드 수정이나 예약 변경을 하지 마.
```

### 성공 증거

- 오전 관찰과 오후 확인의 데이터 차이가 표에 있음
- 미완성 일봉을 확정값처럼 쓰지 않는 테스트 계획이 있음
- LLM과 정량 규칙의 경계가 유지됨
