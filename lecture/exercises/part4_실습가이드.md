## 실전 프롬프트 공식 (CH2 · 강사 라이브 시범)

> 트랙을 직접 고치기 전에, **AI에게 코드를 맡기는 "프롬프트 공식"**을 먼저 익힙니다.
> 같은 요청도 어떻게 말하느냐에 따라 결과가 갈립니다.

### 핵심 공식

```
[현재 상태] + [원하는 결과] + [유지할 제약]
```

- **현재 상태**: 지금 코드가 무엇으로 되어 있는지 (파일·상수·함수명까지)
- **원하는 결과**: 무엇으로 바꾸고 싶은지 (구체적 숫자·조건)
- **유지할 제약**: 깨지면 안 되는 것 (함수 이름·입출력 형태, 나머지 구조)

### Bad vs Good

| ❌ Bad | ✅ Good |
|---|---|
| "코드 좀 고쳐줘" | "현재 screening.py는 거래량 5배 기준이야. RSI 30 이하 + 거래량 3배로 바꿔줘. 함수 시그니처는 유지해줘." |

### 자주 쓰는 3가지 패턴

> 아래 사례는 강사가 PRISM을 1년 운영하며 코딩 에이전트에게 **실제로 보낸 프롬프트**입니다 (일부 축약).

**① 수정 요청** — 현재 상태 + 원하는 결과 + 유지할 제약
```
강사 실제 사례 (2026-01, 매수/매도 에이전트 프롬프트 튜닝):
"아래 요구사항에 대한 계획과 실행을 진행해줘. 기존 에이전트 프롬프트의 결을
완전히 벗어나지 않으며, 과도하게 프롬프트를 증가시키지 않으며,
과적합을 주의하며 프롬프트를 수정하면 돼."

(틀) "현재 ___는 ___야. ___로 바꿔줘. ___는 유지해줘."
```

→ 포인트: 바꿀 것(요구사항)보다 **지킬 것(결·분량·과적합 주의)을 더 길게** 적었습니다. 제약을 명시하면 AI가 멋대로 '개선'하지 않습니다.

**② 에러 해결** — 에러 메시지를 그대로 + 원인 설명 요청
```
강사 실제 사례 (2026-01, 배치 파이프라인 장애):
"오케스트레이터를 돌리는데 '6. Tracking system batch' 단계부터 에러가 나서
실제 매수/매도 에이전트가 잘 안 돌아가. 최근에 데이터 라이브러리를
교체했는데 거기서 문제가 발생한 것 같아."

(틀) "이 에러가 났어: [에러 메시지 붙여넣기]. 원인 설명하고, 고친 뒤 같은 실행을 다시 검증해줘."
```

→ 포인트: 증상(어느 단계에서 났는지) + **최근에 무엇이 바뀌었는지**를 같이 줬습니다. AI가 원인을 넘겨짚지 않게 하는 가장 싼 방법입니다.

**③ 이론-코드 갭 점검** — 내 이론 vs 코드(AI 동작) 일치 확인
```
강사 실제 사례 (2026-01, 매수 기준 완화 후 점검):
"저번에 너랑 같이 강세장에 대해 매수 기준을 완화했어. 그 이후 며칠 더
지켜본 결과, 모델이 오히려 점수를 6점 줄 것을 5점 주는 식으로
손실회피를 억지로 하고 있는 느낌을 받았어."

(틀) "이 코드가 내 이론을 정확히 반영하는지 확인해줘. 내 이론: ___"
```

→ 포인트: 수정이 '돌아간다'에서 끝내지 않고 **실제 결과를 며칠 관찰한 뒤 의도와 다른 동작을 근거로 재점검**시켰습니다. 여러분의 "전후 비교"가 바로 이 습관의 시작입니다.

> 트랙 A~D는 **CH3(수강생 실습)**에서 이 공식을 직접 적용하는 부분입니다.

> 이 중 **수급·재무·산업·시장은 규칙(실데이터 지표)**, **기술·뉴스·전략은 LLM 에이전트**가 담당합니다.

> ⚠️ **중요 — 프롬프트 변경 효과는 LLM을 연결해야 보입니다.**

## System Completion Lane — 내 전략을 관찰 가능한 시스템으로 완성

이 단계는 새 전략 트랙이 아닙니다. 먼저 **트랙 A/B/C/D 중 하나**를 골라 수정하고 데모 검증에 성공한 뒤에만 진행합니다. 전략을 한 파일에 안전하게 반영하는 것이 첫 번째 성공이고, 같은 실행의 데이터 기준일·단계 이벤트·알림·주문 상태·대시보드를 서로 맞춰 보는 것이 두 번째 성공입니다. 다섯 번째 전략 트랙을 만들거나 A/B/C/D를 한꺼번에 고치지 않습니다.

### 코딩 에이전트에 입력

```text
내가 선택한 트랙 A/B/C/D 한 개의 전략 검증이 끝났어. 이제 lecture-prism의 System Completion Lane을 진행해줘.

목표:
- 같은 파이프라인 실행 한 건이 어디까지 진행됐고 무엇을 판단했는지 증거로 확인한다.
- 금요일처럼 가장 최근 영업일 데이터를 사용했다면 오늘 날짜로 꾸미지 말고 실제 data_as_of를 표시한다.
- 알림이나 주문이 실패해도 전략 판단 결과와 실패 상태를 함께 남긴다.

검증 순서:
1. API 키 없이 기본 파이프라인이 여전히 완주하는지 먼저 확인해줘.
2. 최신 실행의 run_id 하나를 고정하고, pipeline event의 sequence가 시작부터 완료 또는 실패까지 순서대로 이어지는지 확인해줘.
3. profile, data_source, data_as_of, market_status를 표로 보여줘. 휴장일이면 최근 영업일 데이터라는 사실을 분명히 써줘.
4. Discord는 필수 채널로 단계별 메시지 전달 상태를 확인해줘. Telegram이 설정되어 있으면 같은 run_id와 sequence가 전달되는지 parity를 확인하고, 설정되지 않았으면 “선택 채널 미설정”으로 표시해줘.
5. 알림 실패는 해당 채널의 failed 상태로 기록하되 파이프라인은 계속 실행되는 fail-open 동작인지 확인해줘.
6. 주문 상태를 accepted(주문 접수), partial_fill(부분 체결), filled(전량 체결), blocked(안전 차단), live_blocked(실거래 차단)로 구분해 설명해줘. accepted를 체결로 쓰지 말고, 포트폴리오에는 partial_fill을 포함한 실제 filled_qty만 포함해줘.
7. 대시보드에서 표시한 run_id가 위에서 고른 실행과 같은지, data_as_of·알림·주문·분석 6섹션·교훈이 모두 같은 실행인지 확인해줘.
8. 화면 공유용 증거에는 실행 상태와 가려진 식별자만 남겨줘. 웹훅 URL을 제출하지 말고, 봇 토큰을 제출하지 말고, 계좌번호를 제출하지 말고, .env를 제출하지 마. 시크릿 값은 출력하지 마.
9. LECTURE_ALLOW_REAL_BROKER=0과 LECTURE_ALLOW_REAL_KIS=0을 유지하고 실제 주문은 절대 보내지 마.

마지막 보고는 “전략 변경”, “실행 진실”, “알림 전달”, “주문 진실”, “대시보드 증거”, “시크릿 점검” 여섯 항목으로 정리해줘.
```

### 완료 증거 체크리스트

- [ ] 트랙 A/B/C/D 중 한 트랙만 바꾸고 관련 데모가 성공했다.
- [ ] 실제 `data_as_of`, `run_id`, 시작부터 끝까지의 `sequence`를 확인했다.
- [ ] Discord 전달 상태가 보이며, 선택한 경우 Telegram도 같은 실행을 가리킨다.
- [ ] `accepted`·`partial_fill`·`filled`·`blocked`·`live_blocked`를 서로 바꿔 말하지 않았다.
- [ ] 대시보드의 포트폴리오는 `partial_fill`을 포함한 실제 `filled_qty`만 보여주고 현금·평가액을 꾸며내지 않는다.

### 결과 제출 (선택) — 본인 이름 브랜치로 push

GitHub 제출은 선택입니다. 오늘의 성공 기준은 먼저 “내 전략이 데모 모드에서 실행되는 것”입니다. 제출이 막히면 화면 공유나 결과 캡처로 대체해도 됩니다.

직접 Git 명령어를 치지 말고 코딩 에이전트에게 아래처럼 맡기세요.

```text
내 실습 결과를 제출할 수 있게 Git 작업을 도와줘.

조건:
1. 현재 변경 파일을 먼저 보여주고, API 키·토큰·DB 파일 같은 민감한 파일이 포함되어 있지 않은지 확인해줘.
2. main 브랜치가 아니라 내 이름 브랜치에서 작업하게 해줘. 브랜치 이름은 [본인이름-영문] 으로 해줘.
3. 변경 내용을 커밋해줘. 커밋 메시지는 "내 전략 적용"으로 해줘.
4. 원격 저장소에 내 이름 브랜치를 push해줘.
5. push가 실패하면 collaborator 권한 문제인지, 로그인 문제인지, 원격 저장소 문제인지 구분해서 설명해줘.

위 과정에서 필요한 Git 명령은 네가 실행하고, 각 단계 결과를 나에게 확인시켜줘.
```

> 푸시가 안 되면: 강사에게 collaborator 초대를 받았는지 확인. 자세한 흐름은 루트의 `README.md` 참고.
> 화면 공유가 기본 — 푸시는 원하는 사람만.
